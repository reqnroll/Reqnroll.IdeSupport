* Client-side `UnhandledException` telemetry is now attributable: VS, VS Code and Rider each generate a per-IDE-session `ClientSessionId`, send it on every event and pass it to the language server as `--client-session-id` so the server's events carry it too (a client exception joins to its `ServerSessionStarted`), and VS Code and Rider now send the same sanitized `StackFrames` as the server and Visual Studio (only the extension's own frames; no paths or file names). `telemetry/queries/error-rates.kql` reports distinct sessions affected (VS, VS Code, Rider, LSP server) - see #1199

* A configuration file with an invalid value (for example a bad `reqnroll.version` in `reqnroll.json` or an invalid tag prefix in `specsync.json`) no longer discards every other configuration setting: only the offending file is skipped (with a warning in the log) and the settings from the remaining valid files still apply.

* `.editorconfig` sections now follow the EditorConfig glob rules, so common sections such as `[*.{feature,cs}]`, `[*.{cs,vb}]`, `[Step{1..9}.cs]`, `[Login[123].feature]` and `[Login?.feature]` apply to matching files; previously brace alternatives, numeric ranges, `[seq]`, `?` and backslash escapes were not understood and those sections were silently ignored. Section matching stays case-insensitive on Windows and is now case-sensitive on Linux and macOS, as the spec requires. A backslash in a section name is now an escape, as in the spec, rather than a path separator, so a section such as `[src\*.feature]` no longer applies (LSP server, VS, VS Code, Rider) - see #968

* Fixed Visual Studio's native rename (F2 / Ctrl+R,R) on a `.feature` step applying the edit twice and corrupting every touched file - the renamed `.cs` attribute ended up as `"...${float}"t}"` (a syntax error, so the binding vanished and every call site went unbound) and each feature step ended up as `...$180.00.0`. VS's built-in rename client applies the `WorkspaceEdit` in the rename response, and the server also pushes the same edit via `workspace/applyEdit` for the Rename Step context command's benefit; the response is now empty for VS so the push is the only apply. This was latent before: the in-request push used to cancel the rename with "Content Modified" (#654), so VS never received a response to apply (LSP server, VS) - see #671
* `textDocument/rename` is now dispatched on the LSP server's serial lane, so an edit arriving mid-rename can no longer leave it computing one half of a multi-file edit against pre-edit state and the other half against post-edit state (LSP server) - see #671
* Rename Step edits now carry the document version they were computed against, so a client can reject one whose document has moved on rather than applying it at stale offsets - this is what LSP's versioned edits are for, and every edit previously went out unversioned, which is why each client had grown its own ad-hoc staleness check instead (LSP server, VS Code) - see #671
* Fixed Rename Step renaming the wrong step definition when the picker was used to choose between several bindings and the `.cs` file was then edited while the rename prompt was open - adding or reordering an attribute changed what the picker's positional index referred to, and the rename followed the index rather than the binding, producing a perfectly valid edit to a step the user never selected. The chosen binding is now recorded by identity, so the rename finds it wherever it has moved to and reports that it is no longer there instead of falling back to an arbitrary one (LSP server, VS, VS Code, Rider) - see #671
* Fixed Rename Step in Rider intermittently refusing to apply with "the file changed while the rename dialog was open" when nothing had been edited - the check spanned the whole time the dialog was open (during which an edit cannot invalidate the result, since the server computes the edit's offsets after the dialog closes) and compared a stamp that a routine filesystem refresh can change on its own without the content differing, which was especially likely on a bind-mounted workspace. It now covers only the rename request's own round trip (Rider) - see #326, #670, #671
* Fixed the Run CodeLens for a scenario intermittently failing to render while the user was typing elsewhere in the same `.feature` file - the server cancels every in-flight, non-mutating LSP request the moment any edit notification arrives, with no per-document scoping, so an edit anywhere raced the CodeLens's own symbol-tree lookup and came back indistinguishable from "no scenario found here." That lookup is now retried once before giving up (VS) - see #671
* Fixed Rename Step in Rider always reporting a generic "Rename failed" instead of the server's actual reason (an invalid step expression, a project that isn't ready yet, and so on), which #650 had already made VS and VS Code show correctly. The IDE's own LSP layer catches the server's error response, logs it to the internal IDE log, and hands back an empty result indistinguishable from "nothing to rename", so the reason never reached the plugin; the rename request now takes a path that preserves it. A rename that times out is also now reported as a timeout rather than as a rejected rename (Rider) - see #655
* Fixed every project nested inside a solution folder being invisible to the extension - Visual Studio's project list is flat (solution folders appear alongside real projects, and the projects inside them are reachable only through the folder's own children), so such a project never reached the LSP server: no binding registry, and step bindings, CodeLens, navigation and inlay hints all silently dead for its `.feature` files. Binding discovery was meanwhile still running against the non-test projects that *were* visible, spawning a connector process per project that failed to load Reqnroll. The solution is now walked recursively, to any nesting depth (VS) - see #729
* Fixed the NuGet-restore-aware project re-send (#690) never arming, leaving a project whose packages were still being restored when Visual Studio first reported it misclassified as having no Reqnroll reference until the next build or solution reload - the subscription was set up on a background thread, where it is not allowed, and threw every time; the failure also wasn't latched, so it repeated for each project and filled the log with warnings (VS) - see #730
* Fixed the Visual Studio extension's log silently dropping lines when two parts of the extension logged at the same moment - several independent loggers appended to the same file, each with its own write lock, so a simultaneous write failed with a sharing violation that was swallowed. The extension now has one shared logger per process: in `devenv.exe` both of its composition roots (VS.Extensibility and VSSDK/MEF) write through it, so messages from the VSSDK side now also reach the "Reqnroll" Output Window pane and the `reqnroll-vs-ext-*.log` file uses one consistent level (`Info`); the out-of-process Run CodeLens components now write their own `reqnroll-vs-codelens-sh-*.log` instead of a second `reqnroll-vs-ext-*.log` distinguishable only by PID (VS) - see #748
* Fixed keyword completion popping up while editing the free-text title of a `Feature`/`Rule`/`Scenario`/`Scenario Outline`/`Background`/`Examples` line, anywhere after the keyword - not just at the end, also in the middle of an already-typed name - accepting a suggestion there deleted the keyword and the whole title, replacing both with just the keyword text. Completion for a block's own keyword now stops once the cursor is at or past that keyword's colon, matching the equivalent boundary step lines already used to stop offering keyword completion once the cursor is in the step text. Also narrows suggestions once anything has been typed on the line: e.g. typing `@` at the start of a line now offers only the tag suggestion, not every block keyword alongside it, and a second `@` right after a complete tag on the same line offers nothing rather than repeating the same tag suggestion - a completion popup while composing a tag or a table is disruptive either way, so this is a deliberate simplification rather than tracking every position Gherkin's grammar would technically still allow a tag (LSP server) - see #818
* Fixed the "Define step" lightbulb only offering "Define all missing steps in file" - never the single-step "Define step: '<text>'" action - when invoked from the first undefined step of a scenario with several undefined steps; every other undefined step already offered both. The per-step action's guard was accidentally keyed off document position (whether the cursor's step was first in the file) instead of off how many undefined steps actually exist, which is what it was meant to check (LSP server) - see #816
* Fixed "Define step" generating invalid C# (duplicated methods and closing braces) when used twice against the same existing file without saving in between - appending a step definition read the target `.cs` file from disk, which still had the pre-edit content while the first edit sat unsaved in the open editor buffer (applied via `workspace/applyEdit`); the second append then computed its insertion point and full-file replace range against that stale content instead of the live buffer the edit would actually land on. Now prefers the same live `.cs` text cache Rename Step already reads from for the same reason, falling back to disk only for a candidate file nothing has opened this session (LSP server) - see #815
* Fixed the Reqnroll Output pane showing a spurious `[Error]` line at startup ("logging 'window hide' failed") when a document was released or closed during solution restore - the diagnostic-only Running Document Table observer called `GetDocumentMoniker` with a cookie that had already gone stale, and VS throws `ArgumentException` for it. That is an expected race in an observe-only monitor, so it is now logged at Verbose instead of Error (VS) - see #814
* Fixed VS Code syntax highlighting turning a mid-line `#` into a comment: a step or description containing text such as `issue #12` or `the colour is #FF0000` had everything from the first `#` onward comment-scoped, because the grammar's comment rule (`#.*$`) matched anywhere on the line. Gherkin comments are line-start only, so the rule is now anchored to the start of the line after optional whitespace (VS Code) - see #1003
* Find Unused Step Definitions telemetry now reports the number of project registries scanned under a correctly-named `ScannedProjects` property - it used to report that same count under `ScannedFeatureFiles`, a name it never actually counted - and reports the request's real `IsCancellationRequested` state instead of always `false` (**note for anyone with saved Application Insights queries/dashboards**: the `ScannedFeatureFiles` property on `FindUnusedStepDefinitions command executed` is renamed to `ScannedProjects`) (LSP server) - see #942, @clrudolphi
* Fixed a SpecSync `specsync.json` tag prefix (`synchronization/testCaseTagPrefix` or each `synchronization/links[]/tagPrefix`) containing a regex metacharacter doing the wrong thing: a `tc.` prefix matched `tcX:123` as if the dot were any character, and an unbalanced metacharacter such as `tc(` produced an invalid tag pattern that made the tag link fail validation and the whole configuration fall back to defaults. The prefix is now treated as a literal and escaped before it is built into the tag pattern (LSP server) - see #966
