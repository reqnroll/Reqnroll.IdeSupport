## Improvements:

* Run CodeLens now resolves each scenario's test target on demand instead of walking the whole `.feature` file on every refresh, fixing it getting stuck on very large feature files (VS, Rider) - see #495
* Run CodeLens's Details popup now has a "Show in Test Explorer" action alongside Run/Debug, jumping straight to the test's native pass/fail state and run history (VS) - see #504
* Run CodeLens now shows the scenario's last-run pass/fail glyph, matching VS's own test CodeLens (VS) - see #504
* Run, hook-match-count, and step-hooks CodeLenses on a `Scenario:` line now appear in a deterministic order (Run, then hook count, then step-hooks) instead of an unspecified tie (VS) - see #504
* Go to Step Definition's ambiguous-match picker now shows the target method's source line instead of a method name/step-type label, built from the standard `textDocument/definition` response instead of a Reqnroll-specific message (VS Code) - see #126
* Post-build binding rediscovery now relies solely on the server's standard LSP dynamic file-watch registration instead of a redundant client-side watcher, after confirming the canonical path reliably detects real `dotnet build`s on its own (VS Code) - see #31
* `.cs` binding methods that fail Reqnroll's structural validation (non-static where required, async void, a malformed step expression or `[Scope(Tag=...)]` tag expression, etc.) now get a live diagnostic squiggle on the offending attribute, merging alongside the IDE's own C# diagnostics for the same file; `.feature` "step not found" diagnostics also now name the specific reason when the step structurally matches an invalid binding instead of a generic message (LSP server) - see #514
* The lightbulb on a `.feature` file now offers quick fixes for a Gherkin syntax error ("Insert '<keyword>'", built from the same expected-token/dialect resolution keyword completion uses) instead of an empty menu; every offered action is now also associated with the diagnostic it fixes, so clients can present it as the fix for that specific squiggle (LSP server) - see #563
* The lightbulb on an ambiguous step now offers a "Go to '<method>'" quick fix for each competing binding (VS Code only - it carries only a navigation command, which only VS Code's LSP client recognizes without a server round trip; Go to Step Definition's existing ambiguous-match picker remains the cross-IDE way to disambiguate) (LSP server, VS Code) - see #563
* Log file timestamps are now consistently UTC (previously a mix of local time, local time with a numeric offset, and - in the Rider plugin - no offset at all, making entries hard to correlate across machines/timezones); on macOS and Linux, the LSP server and its Connector process now write logs to the same platform-appropriate directory the VS Code and Rider clients already used, instead of a different one (LSP server, VS, Rider) - see #625
* Log lines now share one line format (timestamp, level, and the type/file the entry came from) across the file logger, the debug-output logger, and the `Microsoft.Extensions.Logging` bridge, instead of each rendering differently; the VS Code extension's general "Reqnroll LSP" output channel is now also mirrored to a log file, matching VS's and Rider's existing client-diagnostic logs (LSP server, VS, VS Code, Rider) - see #626
* Telemetry event names sent by the LSP server are now defined in one catalog instead of as literals scattered across each call site; the `"Reqnroll Discovery executed"` and bare `"Error"` events are renamed to `"ReqnrollDiscoveryExecuted"` and `"UnhandledException"` respectively to match the naming convention every other event already followed (**note for anyone with saved Application Insights queries/dashboards**: update references to those two event names) - see #627
* Logged operation durations are now consistently whole milliseconds, rounded rather than truncated, across the LSP server's discovery/parse/perf logging and the VS extension's document-initialization logging - previously these varied between tenths-of-a-millisecond, truncated whole milliseconds, and a full `TimeSpan` string depending on which code logged them (LSP server, VS) - see #627
* The Connector (the out-of-process worker the LSP server launches to run binding discovery) now writes its own log file alongside the console output the server captures, so a Connector crash leaves a durable artifact even if the server's own capture missed it; the LSP server's unhandled-exception crash dump now reuses the same file-naming/format conventions as every other log in the family instead of its own one-off filename and a raw, unformatted exception dump (LSP server) - see #628
* The VS Code LSP Inspector log now records each response's round-trip latency (`latencyMs`), matching the VS extension's equivalent log - previously only VS recorded it (VS Code) - see #633
* The Connector no longer writes a log file for every routine, successful discovery run - it buffers in memory and only persists one if something actually goes wrong, or if the LSP server's own `--log-level` is turned up to Info or more verbose, so an active session no longer leaves a dozen-plus small files behind for runs nobody needed to inspect. When it does write one, the LSP server's own "Discovery complete"/"Discovery failed" log lines now include that connector process's PID, so it can be found directly instead of guessed at by timestamp (LSP server) - see #637
* Restored a dedicated "Reqnroll" Output Window pane, showing application-level log messages (Info and above by default) and auto-activating on a warning or worse - the "Reqnroll Language Client" pane VS shows today is VS.Extensibility's own generic LSP protocol trace and never carried the extension's own messages, unlike the legacy Reqnroll.VisualStudio extension's dedicated pane, leaving routine troubleshooting dependent on finding the right per-PID file log (VS) - see #651
* Added the VS Code equivalent of the above: a curated "Reqnroll" output channel showing extension activation, LSP client start/connect/stop, and each command's one-line result, auto-revealing on a warning or worse - the existing "Reqnroll LSP" channel is `vscode-languageclient`'s own generic client channel and never carried curated app-level messages, so "is the extension doing something" had no reliable single place to look (VS Code) - see #661
* The "Reqnroll" Output Window pane (#651) no longer floods with per-request/per-edit internal chatter at its default Info level - ~100 call sites (LSP interception frame bookkeeping, CodeLens/navigation query-response logging, raw JSON-RPC payload dumps, per-edit interceptors, window-activation bookkeeping) were reclassified to Debug/Trace, leaving Information for extension/server lifecycle events and the one-line outcome of an explicit user command; the on-disk support log's own default threshold is also now Warning, matching the LSP server's equivalent file sink. A follow-up audit of the resulting Debug/Trace split then found three services logging their outgoing request params as a raw JSON dump at Debug while the identical incoming raw result dump right below it was at Trace - now consistently Trace in both directions (VS) - see #658
* Added a dedicated "Reqnroll" tool window to the Rider plugin - a curated, app-level console (plugin/LSP-client lifecycle, and the outcome of user-invoked actions like Find Step Usages/Find Unused Step Definitions/Go To Hooks/Rename Step/Run), auto-activating on a warning or worse, matching VS's #651 pane and VS Code's #661 channel; previously the plugin's own diagnostics (`ReqnrollDebugLogger`) were file-only, with no visible console at all - the platform's generic "Language Servers" tool window shows raw per-server LSP traffic for every running server, not curated Reqnroll messages (Rider) - see #662
* Run CodeLens's pass/fail glyph is now sourced from a VSTest logger bundled with the extension, streaming results over a local loopback socket, instead of VS's internal, outline-blind test-outcome push - each Scenario Outline example row now gets its own live pass/fail state and, on failure, the specific step and error message, in place of a single aggregate glyph that previously never updated correctly for outline scenarios; outcomes also now persist across VS restarts, invalidated automatically once the compiled assembly is rebuilt (VS) - see #700, #702
* Run CodeLens now shows per-row Scenario Outline outcomes and failed-step detail, sourced from the same shared LSP-server outcome pipeline and bundled VSTest logger backing VS's Run CodeLens, instead of parsing only a TRX file's aggregate pass/fail after the run exits - falls back to the existing TRX-only result if the server or logger is unavailable for a given run. Only runs started from the Run CodeLens itself feed the glyph: runs started from Rider's own Unit Tests tool window go through JetBrains' `ReSharperTestRunner` host, which never loads VSTest loggers, so the lens doesn't update after those (Rider) - see #700, #702
* Added an opt-in (`reqnroll.testOutcomes.enabled`, off by default) read-only pass/fail CodeLens on `.feature` Scenario/Scenario Outline lines, sourced from the bundled VSTest logger the same way VS's Run CodeLens is - since C# Dev Kit owns test execution in VS Code (#504), this merges the logger into the `dotnet.unitTests.runSettingsPath` setting C# Dev Kit already reads instead of adding a competing Run/Debug affordance; on a Scenario Outline it names which example row failed and on which step (VS Code) - see #700, #702
* Log files now live in a `logs` subfolder of the shared Reqnroll application directory (e.g. `%LOCALAPPDATA%\Reqnroll\logs\` on Windows) instead of directly in its root, where they previously sat alongside unrelated persisted state - `test-outcomes.json`, the telemetry `userid` file, and (VS Code) the generated VSTest runsettings file - making that directory's contents hard to tell apart at a glance, and in the VS Code case put the generated runsettings file at incidental risk of the 10-day log-retention sweep since its name also started with `reqnroll-` (LSP server, VS, VS Code, Rider) - see #726
* Microsoft.Testing.Platform (MTP) test outcomes: the reporter is now compiled from source into each MTP test project, against that project's own Microsoft.Testing.Platform version, instead of a prebuilt DLL pinned to one version - removing the MSB3277/CS1705 version conflicts and runtime type-load failures a different MTP version could cause, and supporting every Microsoft.Testing.Platform 2.x release (2.0.0+). Each IDE connects a project through a project-local `obj/<Project>.csproj.reqnroll-ide.targets` file instead of global or per-user state: VS no longer writes a per-user MSBuild `ImportAfter` file (and removes the one earlier versions wrote), and Rider/VS Code no longer rely on a `CustomAfterMicrosoftCommonTargets` environment variable, so VS Code no longer depends on C# Dev Kit inheriting it. MTP-only test projects (no `Microsoft.NET.Test.Sdk`) are no longer silently skipped in VS. Only Reqnroll projects are touched: VS and VS Code write the `obj/` file only into projects whose NuGet restore output includes a Reqnroll package (and remove it from projects that no longer do), and the build adds the reporter only to projects that reference `Reqnroll.dll`. Opt a project out with `<ReqnrollIdeSupportDisableMtpReporter>true</ReqnrollIdeSupportDisableMtpReporter>` (VS, VS Code, Rider) - see #741, #727
* Step-definition lists now show each binding as it is written on the method - `CalculatorSteps.GivenTheFirstNumberIs - [Given("the first number is {int}")]`, or `[Given]` for a method-name-style binding - so an ambiguous step's competing expressions can be compared at a glance, and an unused `[StepDefinition]` method's per-keyword rows are no longer indistinguishable (Go To Definition in VS; Find Unused Step Definitions in VS, VS Code and Rider). VS Code's Go to Step Definition picker now uses this format too, replacing the source-line label introduced in #126, and lists a binding whose source isn't on this machine with an explanation instead of leaving it out (LSP server, VS, VS Code, Rider) - see #757, #763

## Bug fixes:

* Fixed a failure inside the LSP server, on a request the extension sends on its own behalf (Go To Definition, Find Step Usages, CodeLens, formatting, comment toggling and similar), being reported as an empty result - e.g. "No step definition found" when the server's handler actually threw - with no trace outside the LSP Inspector log; the server's error code and message are now logged at Warning, so they reach the "Reqnroll" Output pane and the log file. Such a request that never gets a response now gives up after 60 seconds, logged at Warning, instead of waiting indefinitely, and every request's round-trip time is logged at Debug (VS) - see #764, #770
* Fixed Go To Definition on a step with several matching step definitions opening a results window titled after the single word under the caret (e.g. `'50' declarations`) - it is now titled after the whole step (`Reqnroll: 2 step definitions for 'Given the first number is 50'`). Its rows now show each binding's method and attribute from the live binding data instead of a declaration line read from the saved file, which showed stale text for unsaved edits (e.g. a method just uncommented). Also fixed every row in the Go To Definition, Find Step Usages and Find Unused Step Definitions results windows appearing twice - once in the Code column and again, wrapped, in an extra Description column. Ctrl+Click still shows the old title - see #761 (VS) - see #757, #763
* Fixed Visual Studio's standard comment shortcuts doing nothing in a `.feature` file - Comment Selection (Ctrl+K, Ctrl+C), Uncomment Selection (Ctrl+K, Ctrl+U) and Toggle Line Comment (Ctrl+/) now work, including from the Edit menu and with custom shortcuts, and each keeps its usual meaning: Comment always adds a `#`, Uncomment removes one `#` from commented lines only, and Toggle uncomments if every line is commented and comments them all otherwise. The Reqnroll "Comment/Uncomment" context-menu command, which was a stop-gap for these shortcuts, has been removed (VS) - see #747, #752
* Fixed installing a newer CI build of an extension not being treated as an upgrade - every CI build of the VS extension carried the same fixed manifest version (`1.0`), and the VS Code and Rider packages the same `0.1.0`, so VS refused a newer build as "already installed". Every CI package now carries `<main version>.<CI run number>` (e.g. `0.1.812`), the same version the .NET assemblies already carried, and CI fails if a packaged extension doesn't. **One-time step:** because the new versions are numerically lower than `1.0`, uninstall a previously installed VS extension before installing a build with this fix (VS, VS Code, Rider) - see #746
* Fixed every step in a `.feature` file inside a **shared project** (`.shproj`) showing as undefined - a shared project was registered by the server as if it were a real project, and because its folder is the innermost one containing its own files it then won the primary-owner rule for them, resolving those files to a binding registry that can never be populated (a shared project has no output assembly of its own). Shared projects and their `.projitems` are now ignored as projects by both the server and the VS glue; their content reaches the server as part of the membership of each project that imports them (LSP server, VS) - see #735
* Fixed `.feature` and binding `.cs` files in a **shared project** (`.shproj`) not being fully attributed to the project that imports it - the Rider plugin's project-folder walk never saw a shared project's files, which live outside the importing project's folder; it now reads the `.projitems` each project imports and adds its `Compile`/`None`/`Content`/`ReqnrollFeatureFiles` items to that project's membership baseline, matching VS and VS Code. Also fixed the Rider plugin sending every `reqnroll/projectFiles` notification with an empty target framework while `reqnroll/projectLoaded` carried the real one, so the server filed the project's membership under a key the project never looked up and fell back to folder-based scanning for all project-wide work (closed-file rescans, reparsing open files, C# diagnostics, rename) - most visibly, step-usage counts on a shared binding class never counted usages from a shared `.feature` file. The Rider plugin's membership also no longer includes the project's own `bin/` and `obj/` folders, whose generated sources (e.g. `AssemblyInfo.cs`, `GlobalUsings.g.cs`) the server otherwise re-scanned for bindings on every change, matching VS (Rider) - see #736
* Fixed binding discovery launching the out-of-process Connector against **every** project the IDE reports, not just Reqnroll ones - in a solution with one Reqnroll test project and twenty ordinary libraries, each build spawned twenty-one Connector processes, every one of them loading an unrelated assembly and its dependency closure into a runtime only to find no bindings, and filling the log with failures for projects that were never expected to yield any. The server now runs discovery only for a project that is a Reqnroll *test* project - it uses Reqnroll (a `Reqnroll*` package reference, or `Reqnroll.dll` next to its output assembly) and owns at least one feature file - matching the gate the legacy Reqnroll.VisualStudio extension applied. `ide.reqnroll.isReqnrollProject` in the project's `reqnroll.json` overrides the detection in either direction (LSP server) - see #731
* Fixed the Run action failing with a generic error when `dotnet` isn't on the IDE process's `PATH` (e.g. macOS GUI-launched apps) - now falls back to `DOTNET_ROOT` and well-known install locations, and shows a specific message when `dotnet` still can't be found (Rider) - see #452
* Fixed the step-usage "N step usages" CodeLens rendering below the binding method's declaration instead of above it, for connector-discovered bindings (LSP server) - see #484
* Fixed F2 doing nothing (or erroring "Rename not available at this location") on a `.cs` binding attribute - now runs Reqnroll's Rename Step, falling back to the native C# rename everywhere else in a `.cs` file so it doesn't hijack renaming an ordinary symbol, including the binding method's own name (VS Code) - see #506
* Fixed every step and hook showing as falsely ambiguous when the reflection connector's and Roslyn's source-file paths for the same file disagree (e.g. a PDB path baked in from a devcontainer/CI build vs. the live workspace path, or a stale/unreadable PDB location) - stale connector-discovered bindings are now also superseded by a path-independent identity check (LSP server) - see #469, #503, #515
* Fixed step-usage CodeLens (and other live-diagnostics features) staying empty for a `.cs` file that was already open when startup reconciliation completed, until the user's first edit - the `didOpen` skip-check now confirms the registry actually has bindings for that specific file instead of only checking that the project's connector had run at all (LSP server) - see #517
* Fixed Go to Step Definition, hook navigation and inlay hints silently doing nothing when the project's assembly was built somewhere else - a devcontainer, a CI agent, another machine, or an external binding package - because the source paths recorded in its PDB don't exist locally. Such a path is now mapped onto the local project where possible; where it can't be, the feature reports why instead of handing the IDE a target it can't open. Find Unused Step Definitions marks those entries as not openable rather than appearing to ignore a click (LSP server, VS, VS Code, Rider) - see #540
* Fixed the binding registry never refreshing after a rebuild in Visual Studio - it only picked up moved/changed step definitions on the next VS restart, leaving Go to Step Definition, hook navigation, inlay hints and CodeLens pointing at stale positions in between. VS never registers the output-assembly file watcher (it doesn't advertise dynamic registration for it), and its build-finished notification was gated on the output path or target framework having changed, which a plain rebuild never does - that notification now always re-triggers discovery, which is a cheap no-op when the assembly genuinely hasn't changed (LSP server, VS) - see #542
* Fixed Find Unused Step Definitions reporting a step from a referenced external assembly (e.g. a class library) twice, attributed to both the referencing project and the project that actually declares it - a project's own discovery run reflects bindings from assemblies it references too, and the reflection connector and Roslyn spell the very same method differently ("DeclaringType.MethodName(ParamType)" vs "Namespace.DeclaringType.MethodName"), so the duplicate copy previously hashed to a different identity and was never recognized as the same binding; identity is now normalized across both discovery paths, and the surviving row is attributed to whichever project's own folder actually contains the source (LSP server) - see #547
* Fixed the step-usage "N step usages" CodeLens permanently reading "0 step usages" for a genuinely-used step declared in a referenced external assembly (e.g. a class library with no `.feature` files of its own) - usage search was restricted to the projects that own the binding's `.cs` file, which never includes the *referencing* project whose `.feature` files actually call it; the search now also covers any project whose own registry independently reports the same binding (LSP server) - see #548
* Fixed the step-usage "N step usages" CodeLens undercounting a method carrying multiple `[Given]`/`[When]`/`[Then]` attributes to just one attribute's own usages instead of the method's total - it looked usages up per-attribute instead of aggregating every attribute anchored at the method's position, the same aggregate query Find Step Usages already used for that spot (LSP server, VS, VS Code, Rider) - see #552
* Fixed the step-usage "N step usages" CodeLens double-counting when an unrelated project (e.g. a parallel multi-targeted sibling project with its own independent copy of the same test suite, no project reference at all) happened to declare a method with an identical normalized signature - the #548 cross-project usage-search expansion matched on that identity alone, folding the sibling's own separate usages in; it now also requires the other project's reported binding to resolve to this exact physical `.cs` file, the signature of a genuine transitive reference (LSP server, VS) - see #552
* Fixed the step-usage "N step usages" CodeLens (and Find Step Usages) occasionally counting every step of one feature file twice for the whole lifetime of a server session, on some launches and not others - the binding match cache updated its match sets and its usage index as separate steps, so two parses of the same document landing at once left the losing parse's steps stranded in the index with nothing backing them; those updates are now atomic. The same document could be parsed twice at once in the first place because the parse coordinator's per-file serialisation did not hold when two schedule calls raced, and because a feature file linked into several projects was re-parsed once per owning project even though only its primary owner's parse is kept - both fixed (LSP server, VS, VS Code, Rider) - see #554
* Fixed the `.cs` binding-source cache throwing under concurrent access (a rename op or a Run CodeLens pass over a large `.feature` file touching several files at once) - its least-recently-used eviction sorted the cache's live dictionary directly instead of a stable snapshot, so a concurrent update could grow the dictionary mid-sort and throw (LSP server) - see #568
* Fixed the connector discovery scheduler occasionally throwing when a project was unloaded (or the server shut down) while a discovery run was still debouncing - it read the just-scheduled run's cancellation token after publishing it, which a concurrent teardown could dispose first (LSP server) - see #568
* Fixed the lightbulb offering to "define" a step consisting of only a keyword with no step text (e.g. a lone `Given`) - there is no text to build a skeleton binding method from, so this quick fix is no longer offered for a step whose text is empty or all whitespace (LSP server) - see #622
* Fixed Find Step Usages doing nothing at all, with no message, when invoked with the caret inside a binding method's body instead of on its attribute or signature line - it now shows the same "the caret is not on a step definition binding" status message VS Code and Rider already show for this case (VS) - see #424
* Fixed Find Step Usages, the Run lens, and Rename Step edit application silently doing nothing for a feature file whose name needs percent-encoding in its LSP URI (e.g. contains a space) - the URI-to-`VirtualFile` lookup was passed the raw encoded URI instead of decoding it first, which only IntelliJ's VFS url format (unlike LSP's) expects (Rider) - see #640
* Fixed Rename Step always failing with "The non-parameter parts cannot contain expression operators" for a binding whose Cucumber Expression contains a literal `$`, `^`, `*`, `+`, `[`, `]` or `|` (e.g. a currency amount like `the price should be ${float}`) - those characters have no special meaning in Cucumber Expression syntax (only `{ } ( ) \ /` do), but were being validated against the full regex-operator set regardless of which syntax the binding actually uses (LSP server) - see #649
* Fixed Rename Step failures (an invalid new step text, a project that isn't ready yet, Visual Studio rejecting the edit, etc.) showing only a generic "Rename failed"/"Rename is not supported" message with no way to tell why - `textDocument/rename` now returns a real LSP error response carrying the specific reason instead of a bare `null` result, and every client now surfaces it: VS's status bar, VS Code's rename notification (both the native `.feature` path and the custom `.cs` command), and Rider's rename dialog (LSP server, VS, VS Code, Rider) - see #650
* Fixed `--protocol-log-level` having no effect on OmniSharp's own internal request-routing/matching diagnostics, which kept leaking into the client's Output panel (and the dedicated protocol log file) at whatever level the current LSP trace happened to compute, regardless of the flag - OmniSharp's own logging-options post-configuration step was unconditionally overwriting the level `--protocol-log-level` had set (LSP server) - see #660
* Fixed the Run CodeLens log logging the same resolved `RunTestTargetEntry` twice back-to-back - a Scenario Outline row and its own scenario can resolve to the same (line, assembly, type, method) tuple, which is now deduplicated before logging (VS) - see #658
* Fixed a Rename Step that the IDE declined to apply (e.g. Rider discarding the edit because the file changed while the rename dialog was open) permanently corrupting the binding registry - the renamed step definition reported "0 step usages" and every one of its call sites showed an unbound-step diagnostic, surviving a rebuild, a close/reopen, and unrelated edits to either file. The server was committing the registry and match-cache updates a rename implies as soon as it had computed the edit, on the assumption the client would apply it; it now stages them and commits only once the client reports back that it actually did (LSP server, VS Code, Rider) - see #670, #671
* Fixed Rename Step in Visual Studio reporting "Content Modified" for a rename that had in fact succeeded, whenever the rename touched a `.feature` or `.cs` file that wasn't already open. Applying the multi-file edit made VS open those files, and the resulting `didOpen` cancelled the still-in-flight `textDocument/rename` request that had produced it - the edit is now pushed after that request's response rather than during it (LSP server, VS) - see #654, #671
* Fixed Visual Studio's native rename (F2 / Ctrl+R,R) on a `.feature` step applying the edit twice and corrupting every touched file - the renamed `.cs` attribute ended up as `"...${float}"t}"` (a syntax error, so the binding vanished and every call site went unbound) and each feature step ended up as `...$180.00.0`. VS's built-in rename client applies the `WorkspaceEdit` in the rename response, and the server also pushes the same edit via `workspace/applyEdit` for the Rename Step context command's benefit; the response is now empty for VS so the push is the only apply. This was latent before: the in-request push used to cancel the rename with "Content Modified" (#654), so VS never received a response to apply (LSP server, VS) - see #671
* `textDocument/rename` is now dispatched on the LSP server's serial lane, so an edit arriving mid-rename can no longer leave it computing one half of a multi-file edit against pre-edit state and the other half against post-edit state (LSP server) - see #671
* Rename Step edits now carry the document version they were computed against, so a client can reject one whose document has moved on rather than applying it at stale offsets - this is what LSP's versioned edits are for, and every edit previously went out unversioned, which is why each client had grown its own ad-hoc staleness check instead (LSP server, VS Code) - see #671
* Fixed Rename Step renaming the wrong step definition when the picker was used to choose between several bindings and the `.cs` file was then edited while the rename prompt was open - adding or reordering an attribute changed what the picker's positional index referred to, and the rename followed the index rather than the binding, producing a perfectly valid edit to a step the user never selected. The chosen binding is now recorded by identity, so the rename finds it wherever it has moved to and reports that it is no longer there instead of falling back to an arbitrary one (LSP server, VS, VS Code, Rider) - see #671
* Fixed Rename Step in Rider intermittently refusing to apply with "the file changed while the rename dialog was open" when nothing had been edited - the check spanned the whole time the dialog was open (during which an edit cannot invalidate the result, since the server computes the edit's offsets after the dialog closes) and compared a stamp that a routine filesystem refresh can change on its own without the content differing, which was especially likely on a bind-mounted workspace. It now covers only the rename request's own round trip (Rider) - see #326, #670, #671
* Fixed the Run CodeLens for a scenario intermittently failing to render while the user was typing elsewhere in the same `.feature` file - the server cancels every in-flight, non-mutating LSP request the moment any edit notification arrives, with no per-document scoping, so an edit anywhere raced the CodeLens's own symbol-tree lookup and came back indistinguishable from "no scenario found here." That lookup is now retried once before giving up (VS) - see #671
* Fixed Rename Step in Rider always reporting a generic "Rename failed" instead of the server's actual reason (an invalid step expression, a project that isn't ready yet, and so on), which #650 had already made VS and VS Code show correctly. The IDE's own LSP layer catches the server's error response, logs it to the internal IDE log, and hands back an empty result indistinguishable from "nothing to rename", so the reason never reached the plugin; the rename request now takes a path that preserves it. A rename that times out is also now reported as a timeout rather than as a rejected rename (Rider) - see #655
* Fixed every project nested inside a solution folder being invisible to the extension - Visual Studio's project list is flat (solution folders appear alongside real projects, and the projects inside them are reachable only through the folder's own children), so such a project never reached the LSP server: no binding registry, and step bindings, CodeLens, navigation and inlay hints all silently dead for its `.feature` files. Binding discovery was meanwhile still running against the non-test projects that *were* visible, spawning a connector process per project that failed to load Reqnroll. The solution is now walked recursively, to any nesting depth (VS) - see #729
* Fixed the NuGet-restore-aware project re-send (#690) never arming, leaving a project whose packages were still being restored when Visual Studio first reported it misclassified as having no Reqnroll reference until the next build or solution reload - the subscription was set up on a background thread, where it is not allowed, and threw every time; the failure also wasn't latched, so it repeated for each project and filled the log with warnings (VS) - see #730
* Fixed the Visual Studio extension's log silently dropping lines when two parts of the extension logged at the same moment - several independent loggers appended to the same file, each with its own write lock, so a simultaneous write failed with a sharing violation that was swallowed. The extension now has one shared logger per process: in `devenv.exe` both of its composition roots (VS.Extensibility and VSSDK/MEF) write through it, so messages from the VSSDK side now also reach the "Reqnroll" Output Window pane and the `reqnroll-vs-ext-*.log` file uses one consistent level (`Info`); the out-of-process Run CodeLens components now write their own `reqnroll-vs-codelens-sh-*.log` instead of a second `reqnroll-vs-ext-*.log` distinguishable only by PID (VS) - see #748
