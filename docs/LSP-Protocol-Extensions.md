# LSP Protocol Extensions — Reference

> **Status:** Reference doc, generated by inventory of the codebase (2026-09-13). Not a design
> doc — no open decisions here. Reflects the code as of branch `fix/671-rename-apply-lifecycle`.
> If a method or DTO shape changes, this doc goes stale like any other reference doc in `docs/`
> (see the Overview doc's design-docs-drift note) — re-verify against source rather than trusting
> it blindly for anything load-bearing.
> **Audience:** Core team contributors, especially anyone adding a new IDE client or a new
> server-side feature that needs to reach a client.
> **Canonical source of truth:** [`LspMethodNames.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Protocol/LspMethodNames.cs)
> on the server; [`lspMethods.ts`](../src/VSCode/src/lsp/lspMethods.ts) (VS Code) and
> [`ReqnrollLanguageServer.kt`](../src/Rider/src/main/kotlin/com/reqnroll/ide/rider/lsp/protocol/ReqnrollLanguageServer.kt)
> (Rider) on the clients. This doc summarizes those; when they disagree, they win.

## 1. Custom `reqnroll/*` messages

15 custom methods in total. All are registered server-side in
[`LanguageServerOptionsExtensions.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Hosting/LanguageServerOptionsExtensions.cs)
(lines 119–291) via manual `OnRequest`/`OnNotification` routing (not MediatR `AddHandler`, because
these DTOs don't implement OmniSharp's `IRequest` marker interfaces).

### Client → Server notifications

| Method | Params | Purpose |
|---|---|---|
| `reqnroll/projectLoaded` | `ReqnrollProjectLoadedParams` — workspaceFolder, projectFile, projectFolder, outputAssemblyPath, targetFrameworkMoniker, defaultNamespace, packageReferences[] (packageId, version, installPath) | Project metadata push on load |
| `reqnroll/projectUnloaded` | `ReqnrollProjectUnloadedParams` — projectFile | Project removed from workspace |
| `reqnroll/projectFiles` | `ReqnrollProjectFilesParams` — projectFile, targetFrameworkMoniker, kind (`Baseline`/`Delta`), files[] (path, role, added) | Project file-membership sync |
| `reqnroll/documentActivated` | `DocumentActivatedParams` — uri | VS tab-activation tracking (drives the didOpen skip-heuristic) |
| `reqnroll/selectRenameTarget` | `SelectRenameTargetParams` — uri, version, attributeIndex | Client's choice when a rename location has multiple candidate attributes |
| `reqnroll/renameApplied` | `RenameAppliedParams` — uri, applied | Client confirms whether its rename edit was actually applied, before the server commits cache updates (see [`RenamePostApplyCoordinator.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/Rename/RenamePostApplyCoordinator.cs)) |

### Client → Server requests

| Method | Params | Response | Notes |
|---|---|---|---|
| `reqnroll/findStepUsages` | standard `ReferenceParams` | `FindStepUsagesResponse` — isBinding, locations[] (uri, startLine/Char, endLine/Char, stepText?, keyword?, scenarioName?, projectName?, featureName?, ruleName?) | Distinct from `textDocument/references` because the server needs to return `null` (three-state result) and per-location `stepText` from the in-memory snapshot, which the standard method can't carry |
| `reqnroll/goToHooks` | `GoToHooksParams : TextDocumentPositionParams` + `ownLevelOnly` | `GoToHooksResponse` — hooks[] (uri, startLine/Char, hookType, hookOrder, methodName) | |
| `reqnroll/goToStepDefinition` | standard `TextDocumentPositionParams` | `GoToStepDefinitionResponse` — items[] (same item shape as `findUnusedStepDefinitions`; projectName always null) | Issue #757. Same bindings as `textDocument/definition`, plus class/method/expression and unresolved-source rows, for VS's multi-definition results list |
| `reqnroll/goToMatchingScenarios` | standard `TextDocumentPositionParams` | `GoToMatchingScenariosResponse` — scenarios[] (uri, startLine/Char, scenarioName, isOutline) | |
| `reqnroll/resolveTestTargets` | `ResolveTestTargetsParams` — textDocument, range | `ResolveTestTargetsResponse` — targets[] (declaringTypeFullName, methodName, isParameterized, rowArguments?, rowIndex?) | Issue #262 (test-runner integration) |
| `reqnroll/findUnusedStepDefinitions` | empty params | `FindUnusedStepDefinitionsResponse` — items[] (projectName?, className?, methodName?, bindingExpression?, stepDefinitionType?, sourceFile?, isResolved, recordedSourceFile?, sourceLine, sourceChar) | |
| `reqnroll/renameTargets` | `RenameTargetsParams : TextDocumentPositionParams` + `requireAttributeLine` (VS Code only in practice — see §3) | `RenameTargetsResponse` — targets[] (label, expression, attributeIndex, startLine/Char, endLine/Char) | |
| `reqnroll/documentSymbolHierarchical` | standard `DocumentSymbolParams` | `DocumentSymbol[]` | VS's nav-bar consumes this instead of `textDocument/documentSymbol` because VS flattens the standard hierarchical result |

### Server → Client notifications

| Method | Params | Gating |
|---|---|---|
| `reqnroll/refreshCodeLens` | `RefreshCodeLensParams` — projectName, isFullReplacement | VS only ([`ClientIdeContext.IsVisualStudio`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Hosting/ClientIdeContext.cs)); other IDEs get the standard `workspace/codeLens/refresh` request instead — see [`CodeLensRefreshRequester.cs:29`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/CodeLens/CodeLensRefreshRequester.cs) |
| `reqnroll/semanticTokens` | `PublishSemanticTokensParams` — uri, version, data[] | Push path used because VS doesn't reliably pull semantic tokens; VS Code and Rider pull via the standard `textDocument/semanticTokens/*` requests and ignore this push |

### Client coverage

- **VS Code** ([`lspMethods.ts`](../src/VSCode/src/lsp/lspMethods.ts)) declares 10 of the 15:
  everything except `resolveTestTargets`, `refreshCodeLens`, `semanticTokens`,
  `documentSymbolHierarchical`, `documentActivated`.
- **Rider** ([`ReqnrollLanguageServer.kt`](../src/Rider/src/main/kotlin/com/reqnroll/ide/rider/lsp/protocol/ReqnrollLanguageServer.kt))
  declares 12 of the 15: everything except the three VS-only ones
  (`refreshCodeLens`, `semanticTokens`, `documentSymbolHierarchical`).
- **Visual Studio** has no typed protocol interface; it goes through the raw
  [`LspInterceptingPipe`](../src/VisualStudio/Reqnroll.IdeSupport.VisualStudio.Extension/LspInterception/LspInterceptingPipe.cs)
  with method names as string literals per call site (e.g.
  [`FindStepUsagesService.cs:16`](../src/VisualStudio/Reqnroll.IdeSupport.VisualStudio.Extension/FindStepUsages/FindStepUsagesService.cs)).

### Not wire messages, despite the naming

`"reqnroll/findReferences"` and `"reqnroll/stepDefinitions"` in the VS extension
([`FeatureReferencesDataSource.cs`](../src/VisualStudio/Reqnroll.IdeSupport.VisualStudio.Extension/FindStepUsages/FeatureReferencesDataSource.cs),
[`StepDefinitionsDataSource.cs`](../src/VisualStudio/Reqnroll.IdeSupport.VisualStudio.Extension/FindUnusedStepDefinitions/StepDefinitionsDataSource.cs))
are `ITableDataSource.SourceTypeIdentifier` values for VS's Find Results window — internal VS
plumbing, never serialized over LSP.

## 2. Standard LSP messages carrying custom content

No standard request/response DTO has extra top-level properties bolted on — the server uses
OmniSharp's stock models unmodified everywhere. The customization instead lives entirely inside
the protocol's own designated extensible slots:

| Standard message | Extension point | Custom content |
|---|---|---|
| `textDocument/codeLens` → `codeLens/resolve` | `CodeLens.data` | `{kind: "stepUsage" \| "hookMatchCount", uri, bindingId, sourceFile, sourceLine, sourceColumn}` — see [`StepCodeLensHandler.cs:146`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/CodeLens/StepCodeLensHandler.cs), [`HookMatchCountCodeLensHandler.cs:166`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/CodeLens/HookMatchCountCodeLensHandler.cs) |
| `textDocument/codeLens` | `Command.command` + `arguments` | Custom command ids `reqnroll.findStepUsages`, `reqnroll.noStepUsages`, `reqnroll.goToHooks`, `reqnroll.goToMatchingScenarios`, `reqnroll.noMatchingScenarios`, with positional `[uri, line, col, ...]` args. Client-executed directly, not routed through `workspace/executeCommand` |
| `textDocument/codeAction` | `CodeAction.command` | Client-side navigation commands with `[uri, selectionOptions]` args — see [`AmbiguousStepActionBuilder.cs:73`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/CodeActions/AmbiguousStepActionBuilder.cs), [`DefineStepsActionBuilder.cs:189`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/CodeActions/DefineStepsActionBuilder.cs) |
| `workspace/executeCommand` | registered command id | `reqnroll.toggleComment`, args `[uri, startLine, endLine, mode?]` with optional `mode` `"toggle"` (default) / `"comment"` / `"uncomment"` — see [`CommentToggleHandler.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/Commenting/CommentToggleHandler.cs) |
| `initialize` (result) | `semanticTokensProvider.legend.tokenTypes` | 11 custom token type names (`reqnroll.keyword`, `reqnroll.tag`, `reqnroll.description`, `reqnroll.comment`, `reqnroll.docString`, `reqnroll.dataTable`, `reqnroll.dataTableHeader`, `reqnroll.stepParameter`, `reqnroll.scenarioOutlinePlaceholder`, `reqnroll.undefinedStep`, `reqnroll.ambiguousStep`), no modifiers — see [`ReqnrollSemanticTokens.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/SemanticTokens/ReqnrollSemanticTokens.cs) |
| `textDocument/rename` (result) | `WorkspaceEdit.changeAnnotations` | Annotation ids `reqnroll.rename.feature` / `reqnroll.rename.binding` — standard LSP 3.16 mechanism, custom ids; only populated when the client advertises `changeAnnotationSupport` |
| `textDocument/publishDiagnostics` | `Diagnostic.source` | `reqnroll.binding` for .cs binding diagnostics — see [`CSharpDiagnosticsPublisher.cs:18`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Pipeline/CSharpDiagnosticsPublisher.cs) |
| `telemetry/event` | params (spec: `any`) | `{eventName, properties}` shape — see [`LspTelemetryService.cs:26`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Telemetry/LspTelemetryService.cs) |

Two adjacent things that are **not** protocol extensions, despite looking like candidates:

- `--ide <identifier>` (e.g. `visualstudio`) is a process command-line argument read in
  [`Program.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Hosting/Program.cs), not an
  `initializationOptions` field. No client in this repo populates `initializationOptions` or an
  `experimental` capabilities block.
- VS's `DocumentActivationTrackingInterceptor` re-sends `textDocument/didOpen` verbatim before
  sending `reqnroll/documentActivated` — it reorders delivery, it doesn't add fields to the
  standard notification.

## 3. Client-side verification (VS Code / Rider)

Confirmed by inventory of `src/VSCode/src` and `src/Rider/src/main` (excluding tests): neither
client adds any wire-level customization beyond what's listed above.

### VS Code

- Only the 10 `reqnroll/*` methods in `lspMethods.ts`, plus standard methods via typed
  `vscode-languageclient` descriptors (`CodeLensRequest`, `DefinitionRequest`,
  `ExecuteCommandRequest`, `CodeLensRefreshRequest`, `TelemetryEventNotification`,
  `DidOpen/Change/Save/CloseTextDocumentNotification`) and one raw `'textDocument/rename'` string
  literal in [`renameStep.ts:302`](../src/VSCode/src/commands/renameStep.ts).
- No `initializationOptions`, no `experimental` capabilities.
- `LanguageClientOptions.middleware` ([`extension.ts:339`](../src/VSCode/src/extension.ts))
  installs `manualDocumentSync` (emits standard-shaped `didOpen/didChange/didSave/didClose` for
  `.cs` files — no extra fields, see
  [`manualDocumentSync.ts:97-131`](../src/VSCode/src/lsp/manualDocumentSync.ts)),
  `prepareRename` interception, and `executeCommandDedupe`. All three change *when or whether* a
  standard message is sent, never its payload shape.
- Client-local VS Code command ids that never cross the wire: `reqnroll.showOutputChannel`,
  `reqnroll.goToStepDefinition`, `reqnroll.defineSteps`, `reqnroll.renameStep`,
  `reqnroll.renameStepOrSymbol`, plus the handlers for the server-emitted `reqnroll.findStepUsages`
  / `reqnroll.noStepUsages` / `reqnroll.goToHooks` / `reqnroll.goToMatchingScenarios` /
  `reqnroll.toggleComment` / `reqnroll.findUnusedStepDefinitions` CodeLens commands.

### Rider

- Only the 12 `@JsonRequest`/`@JsonNotification` methods in `ReqnrollLanguageServer.kt`; every
  standard method goes through lsp4j's `textDocumentService`/`workspaceService` with stock
  parameter types (see
  [`ReqnrollRequestSender.kt`](../src/Rider/src/main/kotlin/com/reqnroll/ide/rider/lsp/ReqnrollRequestSender.kt)).
- No `initializationOptions`. The only `initialize`-time customization is
  [`ReqnrollLspServerDescriptor.clientCapabilities`](../src/Rider/src/main/kotlin/com/reqnroll/ide/rider/lsp/ReqnrollLspServerDescriptor.kt)
  (line 125), which flips on **standard** capability flags Rider's generic LSP client doesn't
  advertise by default: `workspace.inlayHint.refreshSupport`, `workspace.codeLens.refreshSupport`,
  and `textDocument.{formatting,rangeFormatting,onTypeFormatting}.dynamicRegistration`. These are
  spec-defined capabilities being advertised truthfully, not custom fields.
- `Lsp4jClient` overrides in `createLsp4jClient` (same file, line 96) — `telemetryEvent`,
  `refreshCodeLenses`, `refreshInlayHints` — are consumers of standard server→client pushes; they
  don't alter payload shape.

### One cross-client discrepancy worth knowing

`reqnroll/renameTargets`'s `requireAttributeLine` flag exists specifically for VS Code's F2
dispatcher, per the server DTO's own doc comment
([`RenameTargetsParams.cs:13`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Features/Rename/RenameTargetsParams.cs)):
it stops an ordinary C# "rename symbol" invoked via F2 from being hijacked into a loose Reqnroll
step rename. Rider sends plain `TextDocumentPositionParams` for this request
([`ReqnrollLanguageServer.kt:76`](../src/Rider/src/main/kotlin/com/reqnroll/ide/rider/lsp/protocol/ReqnrollLanguageServer.kt)),
so the flag is always unset (`false`) there — intentional, since Rider has no equivalent
F2-hijacking concern, but it means "extends `TextDocumentPositionParams` with
`requireAttributeLine`" in §1's table is VS Code's usage, not a universal client contract.

## 4. Adding a new custom message

When adding a `reqnroll/*` method:

1. Add the constant to [`LspMethodNames.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Protocol/LspMethodNames.cs)
   under the "Custom Reqnroll Extensions" section, with an XML-doc `<c>...</c>` reference to the
   literal (existing entries follow this pattern).
2. Register it in [`LanguageServerOptionsExtensions.cs`](../src/LSP/Reqnroll.IdeSupport.LSP.Server/Hosting/LanguageServerOptionsExtensions.cs)
   via `OnRequest`/`OnNotification`. Name the handler after the message it carries, not the
   pipeline role it plays — matches the existing handler names in `Features/*`.
3. Add the matching entry to VS Code's `ReqnrollMethods` in
   [`lspMethods.ts`](../src/VSCode/src/lsp/lspMethods.ts) — its own doc comment says to keep the
   two lists in sync.
4. Add the matching `@JsonRequest`/`@JsonNotification` method to Rider's
   [`ReqnrollLanguageServer.kt`](../src/Rider/src/main/kotlin/com/reqnroll/ide/rider/lsp/protocol/ReqnrollLanguageServer.kt).
5. If VS needs it, add the string literal at the relevant VS extension call site (VS has no
   generated/typed protocol interface — see §1's client-coverage note).
6. Update this doc's tables.
