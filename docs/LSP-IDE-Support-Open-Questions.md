# Open Questions, Accepted Limitations and Settled Decisions

**Status:** Register. Update it when a question is answered, a limitation is accepted or lifted, or a decision is revisited.
**Audience:** Maintainers and agents. Check here before assuming something is decided, and before re-opening something that was.

This is a register, not a design document, so it does not follow the diagram-and-glossary template in the
[README](README.md). It has three parts: what is genuinely **open**, what has been **accepted as a limitation**,
and the **settled decisions** whose rationale is worth keeping so they are not re-litigated by accident. Detailed
design lives in the documents linked from each row.

## 1. Open questions

| # | Question | Where it matters | Current position |
|---|---|---|---|
| O1 | Should a **per-directory** Gherkin dialect override exist (for example a `reqnroll.json` in a subfolder), or is per-file (`# language: <code>` header) plus per-project enough? | Document buffer, completion, formatting | Per-file and per-project are implemented. No per-directory support. Undecided whether it is needed. |
| O2 | Should Visual Studio's **Document Outline window** (Ctrl+Alt+T) be populated? Visual Studio never sends `textDocument/documentSymbol`; that window uses COM / `IVsHierarchy`. | [Feature Designs F9](LSP-IDE-Support-Feature-Designs.md#f9--document-outline) | The navigation-bar dropdowns above the editor (`GherkinDropdownBarClient`) show the Feature/Scenario hierarchy. The Document Outline window itself is not populated; it would need a COM provider and is deferred. VS Code and Rider use the generic handler. |
| O3 | When Visual Studio applies a rename's multi-file `workspace/applyEdit`, is it **one undo transaction or one per file**? | Rename (F16) | Never verified in a live session. A per-file undo would surprise a user expecting one Ctrl+Z to revert the whole rename. Needs a manual Visual Studio check. |
| O4 | What support should there be for **progress notifications** (`$/progress`, `window/workDoneProgress`) during long operations such as the workspace scan or reflection discovery? | Server UX | Not implemented anywhere in the server or clients. |
| O5 | Should step lines also be **`textDocument/documentLink`** targets (Ctrl+hover hyperlinks) as a complement to Go to Definition? | Navigation | `documentLink` is implemented only for clickable tags. Not extended to steps. |
| O6 | Should **debugging** of feature files (breakpoints, step-into) be supported? | [Test-Runner-Integration-Design.md](Test-Runner-Integration-Design.md) | Not built. The generated `#line` pragmas already put `.feature`-relative sequence points in the PDB, so this may be a narrow per-IDE path-mapping problem rather than a full debug adapter. |
| O7 | If **parameter-type inlay hints** are ever built, how should regex capture-group offsets map onto the visible step text when they diverge (for example an outline placeholder `<amount>` versus its expanded example value)? | Inlay hints (F23) | Not applicable yet: only the binding-target hint kind exists. |
| O8 | Will VisualStudio.Extensibility offer CodeLens support that could replace the classic-API bridge used for `.feature` CodeLens? | Run and hook-match lenses on `.feature` files | The bridge is in place and works. Monitor the Visual Studio roadmap. |

## 2. Accepted limitations and standing risks

| # | Limitation or risk | Why accepted | Mitigation or note |
|---|---|---|---|
| L1 | **Linked `.feature` files in VS Code.** A feature file linked into a second project with an MSBuild `Link` item never appears under the linking project in the Explorer, Test Explorer may enumerate fewer projects, and failed-test markers or diagnostics from more than one project can appear on one open document. | VS Code's Explorer is a pure filesystem view with no concept of linked items, so the first symptom can never be fixed there. The others are not fully root-caused beyond the server's primary-owner resolution. | No data-correctness defect found. Not planned for further work. |
| L2 | **`OmniSharp.Extensions.LanguageServer` could become unmaintained.** | It is the chosen LSP framework (see D12). | `LSP.Core` is insulated from the framework layer, so migration (for example to `Microsoft.VisualStudio.LanguageServer.Protocol`) would touch only the server host. |
| L3 | **A test runner can lock the output assembly during reflection discovery**, so a build-triggered registry update fails. | Out of the server's control. | The last valid registry is retained and the user is notified with `window/showMessage`. |
| L4 | **`files.watcherExclude` covering `bin/` in VS Code** breaks any `createFileSystemWatcher`-based rebuild detection, including the standard one the server relies on. | A user setting; applies equally to any approach. | Not addressed. Whether Rider has an equivalent setting is unconfirmed. |
| L5 | **Pull diagnostics (`textDocument/diagnostic`) are unavailable.** | The framework version in use implements the server-side write converters for the pull report types as `NotImplementedException` stubs. | The server stays on push diagnostics. Revisit only if the framework is upgraded or replaced. |
| L6 | **Visual Studio does not support rename change annotations** and negotiates down to the legacy edit shape. | It does not advertise `changeAnnotationSupport`. | Renames apply silently as before; VS Code and Rider show a grouped, labelled preview. |

## 3. Settled decisions

Each row records a decision and the reason it was made. The "Where" column names the document or code that
carries the detail. Do not reverse a decision without addressing its reason.

| # | Decision | Reason | Where |
|---|---|---|---|
| D1 | **Rider needs no PSI bridge** for cross-language Go to Definition. It works through the generic LSP client with `lspGoToDefinitionSupport = true`. Hook navigation (no standard gesture) uses the custom `reqnroll/findHooks` request. | Confirmed live; the PSI-bridge assumption from the early proof of concept did not hold. | [Architecture §6.3](LSP-IDE-Support-Architecture.md#63-rider) |
| D2 | **Formatting.** Document formatting ships through Rider's generic `LspFormattingService` (opt-in `lspFormattingSupport` override). On-type table formatting needs a Rider-specific handler. | Rider's generic client has no bridge for `textDocument/onTypeFormatting`. | [Architecture §6.4](LSP-IDE-Support-Architecture.md#64-cross-ide-client-implementation--server-conditional-logic-matrix) |
| D3 | **Rider compatibility range** is builds `243` to `262.*` (`pluginSinceBuild`/`pluginUntilBuild` in `src/Rider/gradle.properties`), developed against Rider 2024.3.5. | Bump the range together with `platformVersion`. | Architecture §6.3 |
| D4 | **The Binding Connector is launched per request** as a short-lived child process, communicating over stdin/stdout (`OutProcReqnrollConnector` via `ProcessHelper.RunProcess`): target assembly path as an argument, JSON discovery result on stdout, exit code for failure. | Simplest; no port, no pipe, no long-lived process to manage or secure. | [Architecture §7](LSP-IDE-Support-Architecture.md#7-binding-connector) |
| D5 | **All three clients use stdio** to talk to the server. | One transport everywhere; avoids named-pipe name collisions between Visual Studio instances. | Architecture §6 |
| D6 | **Rebuild detection** uses `workspace/didChangeWatchedFiles` on the output assembly via the standard dynamic registration, with output-assembly-path matching filtering the noise of dependency DLLs. Visual Studio needs no such signal: it hooks build events directly (`VsProjectEventMonitor`). | Verified live in VS Code and Rider against real builds, including full rebuilds producing 30+ unrelated DLL events. No client-specific glue was needed. | Architecture §5 |
| D7 | **Telemetry is relayed by the client.** The server emits `telemetry/event`; each IDE host owns the concrete transmitter, all pointing at one Application Insights resource. Events that occur before or independently of the server (install, upgrade) fire client-side. | Captures both server events and pre-server events without three divergent pipelines. | [Telemetry-Events-Inventory.md](Telemetry-Events-Inventory.md), Architecture §9 |
| D8 | **Find Step Usages uses a custom `reqnroll/findStepUsages` request on every client.** | Generic `textDocument/references` dispatch is unreliable on all three IDEs: the C# server intercepts it based on caret position. | [F14](LSP-IDE-Support-Feature-Designs.md#f14--find-step-definition-usages) |
| D9 | **Go to Step Definition answers `textDocument/definition`.** Where several bindings match, Visual Studio's command and VS Code's picker use `reqnroll/findStepDefinitions`, which returns each binding's class, method and attribute through the same `StepAtPositionResolver`. | A step is a specification and its binding the implementation, so `definition` is the right standard message; the custom request exists only to show *why* a step is ambiguous. | [F5](LSP-IDE-Support-Feature-Designs.md#f5--go-to-step-definition) |
| D10 | **Step completion filtering is client-side.** `ReturnAllCompletionMatcher` returns every candidate with `IsIncomplete = false`. | Simplest correct behaviour. The `ICompletionMatcher` abstraction allows a fuzzy matcher later if feedback shows the client filter is insufficient. | [F8](LSP-IDE-Support-Feature-Designs.md#f8--step-completion) |
| D11 | **Project membership is an authoritative `path → {projects}` index**, populated by the optional `reqnroll/projectFiles` notification, with folder-prefix as fallback only. | A linked or excluded file is a many-to-many relationship that folder-prefix membership cannot express. | Architecture §5 Workspace Model; [Feature Designs: linked files](LSP-IDE-Support-Feature-Designs.md#infrastructure-linked-files-and-project-membership) |
| D12 | **LSP framework is `OmniSharp.Extensions.LanguageServer`.** | Best fit for the server model and the existing handler style; alternatives were weighed and rejected. | [Architecture §10](LSP-IDE-Support-Architecture.md#10-alternatives-considered) |
| D13 | **Visual Studio semantic tokens are server-pushed** (`reqnroll/semanticTokens`, gated by `--ide visualstudio`), and the client drives its own `IClassifier` against `IdeSupportClassifications`. VS Code and Rider pull normally. | Visual Studio's built-in colorizer maps token types through a fixed internal table, so custom `reqnroll.*` names render as plain text, and it pulls tokens unreliably. | [F1](LSP-IDE-Support-Feature-Designs.md#f1--gherkin-syntax-highlighting) |
| D14 | **Logging.** The server writes `reqnroll-<ide>-<role>-[debug-]<date>-<pid>.log` under the Reqnroll application directory's `logs` folder (`%LOCALAPPDATA%\Reqnroll\logs` on Windows), pruned after 10 days. Each client writes its own JSON-RPC inspector trace there. The out-of-process Connector logs conditionally (buffered, flushed on error or at `Info`/`Verbose`). Configure through each client's trace-level setting, which maps to the server's `--log-level`. | Users who cannot easily reach the IDE output panel still need logs. | Architecture §9 |
| D15 | **Diagnostics are push-based** (`textDocument/publishDiagnostics`). | See L5. | [F3](LSP-IDE-Support-Feature-Designs.md#f3--gherkin-file-diagnostics) |
| D16 | **Project layout.** The Visual Studio, VS Code and Rider clients live under `src/VisualStudio`, `src/VSCode` and `src/Rider`; shared code is under `src/Core` and `src/LSP`. | Matches the build systems each client needs (net481/VSSDK, npm, Gradle). | [README](README.md#repository-map) |
